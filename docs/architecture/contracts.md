# Contracts

### Owner record
**Owner:** nebari-user-secrets · **Consumers:** none outside this repo
**Promises:** One Kubernetes Secret per owner, named `us-` plus the first 32 hex characters of the SHA-256 of the Keycloak `sub`, holds `record.json` (an `OwnerRecord`, `schemaVersion` 1). Values are sealed with the owner's data key, which is stored wrapped by a master key. The record's `ownerSub` is checked on every read. The encoded record is at most 524288 bytes and holds at most 50 secrets. Writes use `resourceVersion` optimistic concurrency.
**Errors:** A record whose `ownerSub` does not match the requested sub is rejected. An unknown `schemaVersion` is rejected. Oversize records are rejected on write.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Status record
**Owner:** nebari-user-secrets · **Consumers:** none outside this repo
**Promises:** One Kubernetes Secret per owner, named like the owner record plus `-status`, holds per-app delivery status (`DeliveryStatus`: last success time and count, last failure time and reason). A success replaces only the stored success and a failure only the stored failure. Writes are best-effort, at most once a minute per app per replica (a call inside the window writes nothing), and only for pods that passed verification while the guard allowed the call (see Resolve API). It never holds a value.
**Errors:** `SecretStore.RecordDelivery` returns a failed write's error (a skipped call returns nil) and does not retry it within the window; the resolve handler logs one warning naming the app and the owner's record name, never the sub, a token or a value, and the resolve response is unchanged.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Master-key Secret `user-secrets-kek`
**Owner:** nebari-user-secrets · **Consumers:** operators
**Promises:** One Kubernetes Secret named `user-secrets-kek` in the service namespace holds every master key as a 32-byte entry named by its id (`k` plus a UTC timestamp, for example `k20261120T101500Z`) and a `primary` entry naming the id used for new wraps. The service creates it only when it is absent and no owner record exists; if records exist and the Secret is missing or invalid, the service generates no key and fails closed (`503 kek_unavailable`, `key_event kek_unavailable`). Losing it loses every secret, so operators back it up separately from any copy of the records. A backup of the records alone holds no readable value.
**Errors:** A missing, unreadable or invalid Secret (bad entry length, `primary` naming an absent id) gives `ErrKEKUnavailable`. A record naming an id the Secret does not hold cannot be opened.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Admin commands
**Owner:** nebari-user-secrets · **Consumers:** operators (run as one-off Jobs with the service image)
**Promises:** `user-secrets admin rotate-kek` adds a master key, makes it primary and rewraps every record's data key one record at a time with `resourceVersion` concurrency (up to 5 conflict retries per record); reads keep working throughout because each record names its master key. `user-secrets admin retire-kek <id>` removes an id only when it is not primary and no record uses it. `user-secrets admin rotate-dek [--owner <sub>]` replaces the data key and re-encrypts every value for one owner or all owners; a record is never written unless every value re-sealed. Flags: `--actor` (required, recorded in `key_event`), `--namespace` (default `$POD_NAMESPACE`). Uses `KUBECONFIG` when set, else the in-cluster config. Exit status is non-zero on any failure, and a failed rotation names how many owners were done and is safe to re-run.
**Errors:** Refuses to start when the master key cannot be loaded (admin commands never create a master key; only the service's startup does, and only when no record exists). `retire-kek` of the primary, an unknown id or an id still in use fails and changes nothing.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Audit lines: `key_event`
**Owner:** nebari-user-secrets · **Consumers:** admins, log pipelines
**Promises:** JSON lines with `audit: true`, `event: key_event` and `key_event` one of `kek_created` (detail: new id), `kek_rotated` (detail: `<new id> rewrapped=<n>`, emitted once at the end of a fully successful pass), `kek_retired` (detail: id), `dek_rotated` (`owner_sub` set, one line per owner), `kek_unavailable` (detail: reason), `decrypt_failed`. `actor` names the admin for admin commands. No line carries a value, data key or master key.
**Errors:** A failed rotation emits no `kek_rotated` or `dek_rotated` line for the work that did not complete.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Resolve API
**Owner:** nebari-user-secrets · **Consumers:** `user-secrets-init` in workload pods
**Promises:** Over TLS on `:8443` (same certificate as management), HTTP/1.1 only (the server does not negotiate h2), `POST /api/v1/resolve` with exactly one `Authorization` header holding `Bearer <projected ServiceAccount token, audience user-secrets>` (scheme matched without case) and no body. `200 {"secrets": [{"env": "NEBARI_SECRET_<SUFFIX>", "value_b64": "<standard base64>"}, ...]}`, sorted by `env`, always an array (`[]` when the owner has no record or nothing is enabled for the app): exactly the secrets of the pod's annotated `sub` with a binding for the pod's annotated app. A delivered name is always `NEBARI_SECRET_` plus the suffix and matches `^NEBARI_SECRET_[A-Z][A-Z0-9_]{0,63}$`; a stored binding that would not is skipped. Checks run in this order: the guard allows the call; the token passes TokenReview and names an existing pod with the same UID, the label and both annotations, whose `namespace/serviceaccount` is registered for the app; in enforced mode the pod's `creationTimestamp` is strictly later than the guard's `verifiedSince` (both at whole seconds, so the same second is refused; override mode skips this); the record opens. Each returned secret emits one `secret_read` audit line with `"guard": "enforced"|"overridden"`; every denial emits exactly one `resolve_denied` line with the reason and whatever pod identity is known: empty before TokenReview names a pod; for `pod_missing` and `uid_mismatch` the token's namespace, pod name and ServiceAccount with no UID; the UID once it matched the pod (`not_annotated` and later). A pod that is verified but `not_registered` still goes through the age check, so a `not_registered` pod that also predates the guard is answered `pod_predates_guard`. Delivery status is written only when all three hold: the guard allowed the call, the pod passed verification (or was verified but is `not_registered`), and the pod passed the age check (or override mode skipped it). Outcomes recorded: success with the count, or failure `not_registered`, `decrypt_failed`, `kek_unavailable`. Status is never written for `401`, `pod_missing`, `uid_mismatch`, `not_annotated`, `pod_predates_guard`, `guard_not_verified` or `kubernetes_unavailable`. Every resolve response carries `Content-Length`; the status write happens after the response is written and flushed, on a context detached from the request with a 5 s timeout, so a client that disconnects cannot cancel it, and the client reads the whole body without waiting for it. Every response is `Content-Type: application/json` with `Cache-Control: no-store`. Until the master key is loaded every request gets `503 kek_unavailable`. Token verification, the pod read and the record read together run under a 20 s timeout, inside the init client's 30 s budget; the status write keeps its own 5 s timeout. The service's Kubernetes client for these calls (and for the store and master key) shares one rate limit across API groups, set by the chart's `kubernetes.qps` (default 50) and `kubernetes.burst` (default 100); the guard has its own client with client-go's defaults, so resolve traffic never delays its probes. No log line, audit line or error carries a token or a value; values appear only in the `200` body.
**Errors:** Body `{"error": "<code>"}`, except `503 {"error": "guard_not_verified", "reason": "<fixed guard text>"}`. `401 not_pod_bound` (missing, repeated or malformed header, TokenReview rejects the token, wrong audience, or not pod-bound; any Keycloak token); `403 pod_missing`, `uid_mismatch`, `not_annotated`, `not_registered`, `pod_predates_guard`; `404 not_found` (other paths); `405 method_not_allowed` with `Allow: POST`; `500 decrypt_failed` (a value does not open, or the record names another owner; nothing returned, one `key_event decrypt_failed` naming the owner and the secret, or detail `owner_mismatch`); `500 internal` (handler panic); `503 guard_not_verified`, `kek_unavailable`, `kubernetes_unavailable` (TokenReview, pod read or record read failed, or did not finish within the 20 s timeout).
**Reachability:** The chart's NetworkPolicy admits `:8443` only from pods in registered workload namespaces, and gives the service `get` on pods (nothing else) in each of them. A client trusts `nebari-trust-bundle` (key `ca-certificates.crt`, projected into its own namespace) and dials `user-secrets.<ns>.svc:8443`. The token is a kubelet-minted projected ServiceAccount token (audience `user-secrets`); policy A refuses a TokenRequest for that audience from anyone else. Because `verifiedSince` is set 30 s past the API-server time when it moves, a pod created within about 30 s after the guard becomes verified again (or first verifies) is refused `pod_predates_guard` for its lifetime; a later pod resolves.
**Verified by:** `test/e2e/resolve_test.go` on kind (a curl pod in `test-consumer` created as the registered creator): exact delivery for the pod's app only, cross-user isolation, `403 not_annotated` for an unlabelled pod with the projected token, `401 not_pod_bound` for a management token, `500 decrypt_failed` for an entry copied from another owner's record, `503 guard_not_verified` and `403 pod_predates_guard` around a `[Warn]` binding, the delivery status in `GET /api/v1/secrets`, and the `secret_read` and `resolve_denied` lines with no value or token in any service log line.
**Since:** 2026-11-24 (spec: docs/design/user-secrets-spec.md)

### Workload pod metadata
**Owner:** nebari-user-secrets (`cluster/policies.yaml`, `internal/podidentity`) · **Consumers:** registered creators (JupyterHub, dask-gateway) that build workload pods
**Promises:** A workload pod is trusted only with the label `nebari.dev/user-secrets: "true"` and both annotations `nebari.dev/user-secrets-sub` (the user's Keycloak `sub`) and `nebari.dev/user-secrets-app` (a registered app id), set at pod creation. With the bundle installed, policy A (`user-secrets-pod-guard`) refuses a labelled pod without both annotations, an annotated pod without the label, and any later change to the label or annotations (including through `pods/status`), and policy B (`user-secrets-creators`) admits a labelled pod only from a creator registered in `user-secrets-creators` for the pod's namespace and annotated app. Resolve additionally requires the pod's `namespace/serviceaccount` to be registered for the annotated app.
**Errors:** A pod without the label and both annotations is refused by resolve with `403 not_annotated`; a labelled pod from anyone else is refused at admission with `user-secrets: requester is not a registered creator for this namespace and app`.
**Since:** 2026-11-24 (spec: docs/design/user-secrets-spec.md)

### File layout under `/var/run/nebari/secrets`
**Owner:** nebari-user-secrets (`user-secrets-init fetch`, `internal/initfiles`) · **Consumers:** consumer workloads and user code; `user-secrets-env`
**Promises:** The init container (`/user-secrets-init fetch --url <resolve URL> --ca <trust bundle file> --token <projected token file> --dir <files dir> --bin-dir <bin dir> [--mode soft|strict]`, from the service image, UID 65532) writes into the files volume (an `emptyDir`, `medium: Memory`, `sizeLimit: 1Mi`, mounted read-only at `/var/run/nebari/secrets` in workload containers) one file `NEBARI_SECRET_<SUFFIX>` per resolved secret, holding the exact stored bytes (no encoding, no trailing newline added), mode `0440`, group the pod's `fsGroup`. Only names matching `^NEBARI_SECRET_[A-Z][A-Z0-9_]{0,63}$` are written. Each file and `.status` is written to a temporary name starting `.tmp-`, fsynced, chmodded and renamed, so a reader never sees a partial file; a `.tmp-*` file left by a write killed before its rename is removed at the start of the next delivery or failure record. `.status` is written on every fetch outcome except misconfiguration (exit `2`), where it may be absent: `ok <count>`, or `error <code> <detail>`, one line of at most 200 bytes in all, where the code is never cut and `<detail>` is cut to fit (on a UTF-8 boundary, keeping a trailing `after <n> attempts`), is never empty (`-` when there is nothing to add), and never holds a token or a value. Delivery is all or nothing: on any error no `NEBARI_SECRET_*` file is left, including files from an earlier run. Whatever the outcome, the binary copies itself to `<bin dir>/user-secrets-env` (mode `0550`; the bin volume is a disk-backed `emptyDir` mounted read-only at `/var/run/nebari/user-secrets-bin`). Resolve uses a 30 s budget, reads the token on every attempt, and retries a `503` or a connection error with backoff 500 ms doubling to 5 s while another attempt can start within the budget. Each attempt's connect (including the DNS lookup) times out after 5 s and its TLS handshake after 5 s, so a dropped or stalled connection is retried rather than spending the budget; the wait for response headers is 25 s, above the server's 20 s resolve timeout. A missing `.status` means the init container never ran (an injection failure) or exited `2`.
**`.status` codes:** `token_missing` (token file absent or empty), `token_invalid` (token holds a control byte), `ca_missing` (trust bundle absent or holds no certificate; detail names the file), `bad_config` (the resolve URL is not `https://<host>`; misconfiguration, so the init container exits `2` in every mode after recording it), `unreachable` (connection or TLS error; detail ends `after <n> attempts`), any resolve API error code (`not_pod_bound`, `pod_missing`, `uid_mismatch`, `not_annotated`, `not_registered`, `pod_predates_guard`, `not_found`, `method_not_allowed`, `decrypt_failed`, `internal`, `guard_not_verified`, `kek_unavailable`, `kubernetes_unavailable`; detail `http <status>`, with `after <n> attempts` for a retried `503`), `unavailable` (a `503` without a well-formed error code), `bad_response` (another status without a well-formed code, or a `200` body that is not the contract's JSON), `invalid_response` (a `200` entry with an invalid delivered name or a value that is not base64), `write_failed` (a file, a stale-file removal or `.status` could not be written).
**Exit codes:** `0` on delivery, and on any delivery failure in `soft` mode (the default); `1` on a delivery failure in `strict` mode, including a failed copy of `user-secrets-env`, so a `restartPolicy: Never` pod fails and its workload containers never start; `2` on misconfiguration in every mode: a usage error (unknown subcommand, missing or unexpected flag, bad `--mode`; nothing is written) or a malformed `--url` (`.status` `error bad_config`, earlier secret files removed, the wrapper not copied).
**Errors:** See `.status` codes. A failure to record the failure, or to copy the wrapper, is written to the init container's stderr.
**Verified by:** `internal/initfiles` (`TestWriteAllExactBytes`, `TestFetch`, `TestFileWriterFail` and the rest), `cmd/user-secrets-init` `TestInitMain` (exit codes per mode), and `test/e2e/init_test.go` `TestInitDeliversFiles` on kind (the init container as UID 65532, the workload as UID 1000 GID 1000, `fsGroup` 2000: journey 13 bytes byte-identical by SHA-256 when read by the workload user, files mode `0440` group 2000, the wrapper mode `0550` group 2000 and exec'd by the workload user; in a namespace the NetworkPolicy does not admit, `error unreachable` with no files in `soft` and a failed pod whose workload never starts in `strict`).
**Since:** 2026-11-26 (spec: docs/design/user-secrets-spec.md)

### `user-secrets-env -- <cmd> [args]` wrapper behaviour
**Owner:** nebari-user-secrets (`internal/initfiles.ExecWithEnv`, dispatched when `user-secrets-init` runs under the name `user-secrets-env`) · **Consumers:** consumers that export env (the injector prepends `/var/run/nebari/user-secrets-bin/user-secrets-env --` to a workload container's `args` or `command`)
**Promises:** Reads `/var/run/nebari/secrets` and adds each file whose name matches `^NEBARI_SECRET_[A-Z][A-Z0-9_]{0,63}$` to the environment as `NAME=<exact file bytes>`; other files are ignored. Never replaces a variable that is already set, even to an empty value. A value containing a NUL byte is skipped and its name (never the value) written to stderr as `user-secrets-env: skipping <NAME>: value contains a NUL byte`; an unreadable file is skipped the same way with the error. When the directory exists but cannot be listed, it prints `user-secrets-env: no secrets exported: <error>` (in addition to any `.status` warning) and exports nothing; a missing directory prints only the `.status` warning. When `.status` starts with `error`, or is missing or unreadable, it prints exactly one line to stderr, `user-secrets-env: warning: secrets not delivered: <.status line or reason>`, before looking up the command (so the warning also appears when the command is then not found or cannot run), and still runs the command. Then it replaces itself (`execve`) with the command after `--`, looked up on `PATH` unless it contains a `/`, with every argument passed unchanged, so the command's exit status is the container's. No message carries a value.
**Errors:** Returns only when it cannot exec, with a message on stderr: exit `2` when the arguments are not `-- <cmd> [args]`, `127` when the command is not found, `126` when it cannot be executed (the codes `env(1)` and shells use).
**Verified by:** `internal/initfiles` `TestExecWithEnv`, `TestExecWithEnvErrors` (exec seam), `cmd/user-secrets-init` `TestEnvDispatch` (real exec through the `user-secrets-env` name), and `TestInitDeliversFiles` on kind (env vars byte-identical to the files, a container-set variable kept, one warning line for `error unreachable`).
**Since:** 2026-11-26 (spec: docs/design/user-secrets-spec.md)

### Management API
**Owner:** nebari-user-secrets · **Consumers:** nebari-landing (nebari-landing#236)
**Promises:** Over TLS on `:8444`, every route requires `Authorization: Bearer <Keycloak access token>` (scheme matched without case, exactly one token; cookies are never read) and acts only on the token's `sub`. Routes: `GET /api/v1/secrets` (`200` `OwnerView`), `PUT /api/v1/secrets/{name}` with `{"description", "value_b64", "bindings": [{"app", "env"}]}` (`201` created or `200` updated, body `SecretSummary`; `value_b64` is standard base64, required on create, and on update present rotates while absent or `null` keeps; an empty string is rejected as `invalid_value` so a form sending `""` for an untouched field cannot wipe a secret; `description` and `bindings` replace the stored ones), `DELETE /api/v1/secrets/{name}` (`204`), `GET /api/v1/apps` (`200 {"apps": [...]}`), `GET /api/v1/status` (`200 {"guard": {"state", "mode", "reason"}}`, any authenticated user; this replica's guard: `state` is `verified`, `confirmed_bad`, `unknown` or `overridden`, `mode` is `enforced` or `overridden` (config `guard.mode: unverified`), `reason` is a short fixed text such as `binding user-secrets-creators: validationActions lacks Deny`, naming ConfigMap keys but never values; the state is reported, not a readiness gate; each replica evaluates on watch events after a 2 s settle delay (a change that comparison alone shows is applied at once), on a backoff of 2 s doubling to 30 s while not verified (reset on verified and on every watch event), and every 5 minutes while verified). Every response is `Content-Type: application/json` (none on `204`) with `Cache-Control: no-store`, except that Go's `ServeMux` answers paths containing `.`, `..` or `//` with a `307` redirect to the cleaned path (the redirect has no JSON body, and the cleaned path still requires auth). `405` carries an `Allow` header. Request bodies are at most 64 KiB. Write-only: no response, header or log line contains a secret value.
**Errors:** Body is `{"error": "<code>"}` with no `detail`. `401 invalid_token`; `400 invalid_name`, `invalid_suffix`, `unknown_app`, `grants_not_supported`, `limit_exceeded`, `value_required`, `invalid_value` (`value_b64` is not standard base64), `invalid_request` (not JSON, unknown field, any trailing data); `404 not_found` (also any unknown path); `405 method_not_allowed`; `409 env_conflict`; `413 request_too_large`; `500 internal` (a handler panic, logged and recorded on the span); `503 kek_unavailable`, `kubernetes_unavailable`.
**Since:** 2026-11-20 (spec: docs/design/user-secrets-spec.md)

### Creators ConfigMap `user-secrets-creators`
**Owner:** nebari-user-secrets (chart `chart/templates/creators-configmap.yaml`, rendered from `registry.creators`) · **Consumers:** the `user-secrets-creators` ValidatingAdmissionPolicy in `cluster/policies.yaml` (its binding's `paramRef` names this ConfigMap)
**Promises:** One ConfigMap named `user-secrets-creators` in the service namespace. Each registered creator `system:serviceaccount:<ns>:<name>` is one key `<ns>.<name>` whose value is `namespaces=<a,b>;apps=<x,y>`, both lists sorted and comma-joined. The chart and `registry.CreatorsConfigMapData` produce the same data (`test/chart` `TestCreatorsConfigMapMatchesGo`). With no creators the ConfigMap exists with no data.
**Errors:** A creator username that is not exactly `system:serviceaccount:<namespace>:<name>` fails the chart render. A missing ConfigMap makes the policy binding deny (`parameterNotFoundAction: Deny`).
**Since:** 2026-11-23 (spec: docs/design/user-secrets-spec.md)

### Guard-state ConfigMap `user-secrets-guard-state`
**Owner:** nebari-user-secrets (written by every replica's guard, `internal/guard/state.go`) · **Consumers:** the service's replicas only (resolve refuses a pod whose `creationTimestamp` is not later than `verifiedSince`)
**Promises:** One ConfigMap named `user-secrets-guard-state` in the service namespace, created by the first replica that needs it (not by the chart). Keys: `fingerprint` (the guard objects' versions, `vap/<name>=<uid>/<generation>` for both policies, `vapb/<name>=<uid>/<generation>` for both bindings and `cm/user-secrets-creators=<uid>/<resourceVersion>`, joined by `;`, `-` in place of a missing object; no ConfigMap data), `verifiedSince` (RFC 3339 UTC, whole seconds: an API-server time taken after the probes passed, plus 30 s; it never moves backwards), and `badMarker` (present only while a replica has seen `confirmed_bad` since the last move; a random value per marking). Every write uses `resourceVersion` concurrency; a move keeps the later `verifiedSince` and clears `badMarker` only if it is the value that replica observed. Deleting it is safe: the next verified evaluation moves `verifiedSince` and re-creates it.
**Errors:** A missing or unparseable `verifiedSince` counts as absent and makes the next verified evaluation a move. A failed write leaves the guard `unknown`.
**Since:** 2026-11-23 (spec: docs/design/user-secrets-spec.md)

### Consumed: NIC root App-of-Apps reads `apps/*.yaml` in the GitOps dir
**Owner:** nebari-infrastructure-core (implicit; `pkg/argocd/templates/apps/root.yaml`, `pkg/argocd/project.go`, `pkg/argocd/writer.go`, `pkg/argocd/templates/values/keycloak/base.yaml`, `pkg/config/config.go`, `pkg/providers/cluster/local`) · **Consumers:** `test/journeys/register-app.sh`, `test/journeys/gitops`, `test/journeys/seed-keycloak.sh`, `test/journeys` (tag `journeys`)
**Promises (relied on):** With the local repository provider and no path, the GitOps repository is `~/.nic/gitops/<project_name>` on the runner, mounted read-only at the same path into the kind nodes, and the kind cluster is named `<project_name>` (context `kind-<project_name>`). `Application/nebari-root` creates an Argo CD Application for every `*.yaml` in `<gitops-dir>/apps/` (except `root.yaml`), read from the local `file://<gitops-dir>` repo (non-recursive, `include: '*.yaml'`). The `nebari-apps` AppProject admits any source repo, any destination namespace and every cluster- and namespace-scoped kind. Keycloak runs in namespace `keycloak` behind Service `keycloak-keycloakx-http` on plain HTTP port 8080, with the local provider's base path empty; it is started with `KC_HOSTNAME=https://keycloak.<domain>`, so every token's `iss` is `https://keycloak.<domain>/realms/nebari` whichever address Keycloak is reached on, and NIC's own consumers fetch signing keys from the in-cluster Service while checking that external issuer. Tier 3 sets the chart's `keycloak.jwksURL` to `http://keycloak-keycloakx-http.keycloak.svc.cluster.local:8080/realms/nebari/protocol/openid-connect/certs` and `keycloak.issuers` to that issuer. The nebari realm's own `admin` user holds only a plain realm role, so the seed script uses the master realm admin (Secret `keycloak-admin-credentials`, key `admin-password`). The landing page is deployed into `nebari-system` by the `nebari-landing` chart, whose frontend pods carry `app.kubernetes.io/name: nebari-landing` and `app.kubernetes.io/component: frontend`.
**Errors:** A renamed directory, project, Service, port or hostname formula breaks Tier 3 at registration, at token validation (`401 invalid_token` on every management call) or at seeding; nothing in this repo detects it before a Tier 3 run.
**Verified by:** a Tier 3 run (`TestChartConvergesOnNebari`, `TestManagementOnNebari`, which also checks the token's `iss`); `gh api repos/nebari-dev/nebari-infrastructure-core/contents/<path>?ref=<tag>` for the files above.

### Pins file `ci/pins.env`
**Owner:** nebari-user-secrets · **Consumers:** Makefile (`include`), `test/e2e/setup.sh`, `test/policy/run.sh`, `test/policy/run-all.sh`, `hack/kind.sh` (through `ci/load-pins.sh`), `.github/workflows/*.yml` (appended to `$GITHUB_ENV`), the Tier 1 catalog test and `test/journeys/cmd/summary`
**Promises:** Every external version the CI tiers depend on is written here and nowhere else: one `KEY=value` line per pin with a `#` comment naming its source. Keys are upper case and unique. Values are literal text (no quotes, no `$(`, backtick or `${`) and hold no spaces, except `POLICY_K8S_VERSIONS`, which is space-separated. Bash readers load it with `ci/load-pins.sh`, which exports each line as literal text and never `source`s the file. The copies that cannot read the file (`guard.PauseImage`, the Dockerfile's `ARG GO_BUILDER_IMAGE` default, the workflows' `nebari-dev/deploy-nebari-action` `uses:` refs) are cross-checked against it by `TestPinsMatchSources`, which also fails on any other copy of a pin value outside docs, `test/policy/results` and the vendored NIC fixtures.
**Errors:** A missing key is a reader error, never a silent default (`: "${KEY:?}"` in bash, `Pins.Require` in Go). A malformed line, a duplicate key or a shell expansion in a value fails `LoadPins` and so Tier 1.
**Since:** 2026-11-24 (spec: docs/superpowers/specs/2026-11-24-ci-tiers-design.md)

### Journey catalog `test/journeys/catalog.yaml`
**Owner:** nebari-user-secrets · **Consumers:** the Tier 1 catalog test (`test/journeys/catalog`), `test/journeys/cmd/summary` (job summaries), `docs/ci/coverage.md` (generated by `make coverage-doc`)
**Promises:** The single source for features, journeys, CI checks, their tiers, statuses (`covered`, `planned`, `not-covered`), test names and reasons, with the schema of `catalog.Catalog` (unknown fields rejected). A `covered` check names test functions that exist under its tier's build tags (tier 1: no tag; tier 2: `e2e` or `integration`, or `run.sh:<section label>` of the policy matrix; tier 3: `journeys`). A `planned` check has a reason and the slice that adds its test; a `not-covered` check has a reason. Every journey in the service spec's Journeys table has an entry, and every active feature has a journey. Feature ids are never reused.
**Errors:** Any violation, a stale `docs/ci/coverage.md`, or a workflow reading a secret other than `secrets.GITHUB_TOKEN` fails `TestRepoCatalog` and so Tier 1.
**Since:** 2026-11-24 (spec: docs/superpowers/specs/2026-11-24-ci-tiers-design.md)

### Required check names
**Owner:** nebari-user-secrets (`.github/workflows/ci.yml`, `.github/workflows/journeys.yml`) · **Consumers:** the `main` ruleset and merge queue (set by the user)
**Promises:** The CI jobs report these check names: `tier1`, `tier2-e2e`, `tier2-policy (v1.30.13)`, `tier2-policy (v1.32.11)`, `tier2-policy (v1.34.3)` and `tier3`. The `tier2-policy` names are `tier2-policy (<version>)` for each version in `POLICY_K8S_VERSIONS`, so changing that pin changes the names. Every check runs on `pull_request`, `merge_group`, `v*` tags and `workflow_dispatch` (`tier3` reports as skipped on `pull_request`), reads no secret other than the workflow's own `GITHUB_TOKEN`, and its job summary shows the commit (and merge queue head and base), every pin and the tier's catalog checks; `tier3`'s also shows the NIC release and whether it is `BLOCKING`. `tier3` fails on test failures only while the latest NIC release contains `NIC_REQUIRED_COMMIT`, and in every mode (a `merge_group` run while non-blocking included) when the gate cannot decide (the GitHub API unreachable after retries); until then a `merge_group` run skips everything after the gate and passes, and other runs report failures as warnings.
**Errors:** The ruleset matches checks by name, so a renamed job, or a changed `POLICY_K8S_VERSIONS`, leaves a required check waiting forever. Renaming a job or changing the versions is a contract change: update this entry and the ruleset together.
**Since:** 2026-11-24 (spec: docs/superpowers/specs/2026-11-24-ci-tiers-design.md)

### Make targets for the kind tiers
**Owner:** nebari-user-secrets (Makefile) · **Consumers:** `.github/workflows/ci.yml`, the plan's validation commands, developers
**Promises:** `make e2e-up` builds the image and brings up `us-e2e` (kubeconfig `.kube/e2e`); `make e2e-test` runs `go test -tags e2e ./test/e2e/...` against it; `make policy-test` runs the policy matrix on a throwaway kind cluster per version in `POLICY_K8S_VERSIONS`, or only `K8S_VERSION=<kindest/node tag>` when given, and writes each transcript to `test/policy/results/<version>.txt`. Versions come from `ci/pins.env`. `make policy-test` exits non-zero when any version's cluster create fails or any expect fails, after running every version and deleting each cluster. Integration tests (`-tags integration ./internal/...`) use `.kube/kind`, or `USER_SECRETS_TEST_KUBECONFIG` when set (relative to the repo root unless absolute); CI sets it to `.kube/e2e`.
**Errors:** A missing pin stops the harness before it creates a cluster.
